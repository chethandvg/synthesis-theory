# Golden vectors

Each `*.json` file here is a list of input/output cases that the Rust crate, the Python bindings and the WebAssembly bindings must all reproduce. The format is `golden-vectors@1` from [evidence-kernel](https://github.com/chethandvg/evidence-kernel).

The vectors are generated by [`generate.py`](generate.py), the reference (oracle) implementation. Nothing in it calls the Rust code. It has two parts:

- **`lifesound.py`'s instruments**, copied from the project's earlier Python toolkit and run with numpy, with the two deliberate changes that signal-core's oracle makes: a pure-Python port of SplitMix64 (signal-core's generator) replaces numpy's random generator, and `exp_decay` uses ln 1000 instead of the rounded 6.907755. The SplitMix64 port is copied from [signal-core's `vectors/generate.py`](https://github.com/chethandvg/signal-core/blob/v0.1.0/vectors/generate.py), because one repo's Python cannot import another's; only its `uniform` method is needed here.
- **Exact or certified references for the theory**: `karplus_strong_pitch` as an exact fraction `sr / (N + 1/2)`, its detuning in cents with mpmath at 50 digits, the FM sideband amplitudes from mpmath's Bessel functions `Jₙ(I)`, and the roots of `cos x · cosh x = 1` certified with interval arithmetic (mpmath.iv). `karplus_strong_tuned` and `fm_tone` are not in `lifesound.py`; their reference is a plain-Python loop and a numpy formula.

Regenerate with:

```bash
python vectors/generate.py   # needs numpy and mpmath
```

The script certifies the free-bar roots (the check of the V claim `synth:BAR-MODES`) before it writes anything, and stops if any step fails: there is no root in (0, 2] (an alternating-series bound), every piece of [2, 28] either has `f = cos x · cosh x − 1` of one sign or `f′` of one sign with a sign change of `f` (one root), and each of the eight roots is bisected to an interval narrower than 1e-45 whose two ends round to the same double, so the expected value is the correctly rounded root.

| File | Functions | Tolerance |
|---|---|---|
| [`instruments.json`](instruments.json) | `modal_chime`, `fm_bell`, `soft_voice`, `heartbeat` | 1e-12 |
| [`strings.json`](strings.json) | `karplus_strong`, `karplus_strong_tuned` (1e-12), `karplus_strong_pitch` (exact), `karplus_strong_detune_cents` (1e-12) | 1e-12 |
| [`fm.json`](fm.json) | `fm_tone` (1e-12), `fm_spectrum` (1e-12 absolute) | 1e-12 |
| [`bar_modes.json`](bar_modes.json) | `free_bar_roots`, `free_bar_ratios` | 1e-15 relative |
| [`errors.json`](errors.json) | invalid input, in every function (the crate's own input rules, not oracle output) | — |

Tolerances are `max(abs, rel · |expected|)`. Why each is what it is (the largest differences measured with the Python bindings are in brackets):

- **1e-12 (`rel = abs = 1e-12`)** for the instruments and strings, as in signal-core: the crate evaluates the same formulas in the same order as numpy, and the remaining differences come from numpy's own `sin`, `exp` and `pow` and from its pairwise sums (the burst's mean). Most cases agree exactly; the largest differences are 1.3e-13 for `soft_voice`, whose pitch the crate computes through pitch-math (`freq · 2^((69 + c/100 − 69)/12)` instead of `freq · 2^(c/1200)`, a few ulps apart) and integrates over hundreds of samples, 2e-16 for the strings, and 2e-13 for the detuning in cents, where `1200 · log₂` turns one ulp of the frequency ratio into about 1.7e-13 cents. The `soft_voice` difference grows with the length of the signal, so 1e-12 holds for these vectors (at most 600 samples) but not for long voices with vibrato: measured against `lifesound.py` at 44.1 kHz, it is 7.8e-13 after 1 s and 1.4e-12 after 2 s at 220 Hz, and 1.5e-11 after 10 s at 440 Hz.
- **Exact** for `karplus_strong_pitch`: `sr / (N + 0.5)` is one correctly rounded division of exact numbers, the same double as the exact fraction rounded.
- **1e-12 absolute** for `fm_spectrum`: the expected amplitudes are exact Bessel values, the measured ones the discrete Fourier transform of a 44 100-sample floating-point tone, so they differ by rounding in the tone and in the 44 100-term sums [1.8e-14]. The tolerance is absolute because some amplitudes are 0 (a sine at 0 Hz or at `sr/2`) or below 1e-10.
- **1e-15 relative** for the free-bar roots and ratios: the crate bisects to adjacent doubles, so a root can differ from the correctly rounded value only through the rounding of `cos` and `cosh` near it (a few ulps, up to about 1e-15); on the tested platforms it is exact [0], and the ratios, squares of quotients, differ by at most 3.2e-16.

To keep the files small, every case uses a short signal (at most a few hundred samples, often at a low sample rate such as 400, 1000 or 8000 Hz), except `fm_spectrum`, which renders one second internally but stores only its 9 to 31 amplitudes. Every case names the claim in [`claims.yaml`](../claims.yaml) that it tests. A JSON `null` is `None` in Rust and Python and `null` in JavaScript (`pluck_brightness_hz` for an unfiltered pluck). The pitch measurements of rendered strings (`synth:KS-DETUNE`, `synth:KS-TUNED`) need seconds of audio, so they are property tests in [`tests/properties.rs`](../tests/properties.rs), not vectors here.
